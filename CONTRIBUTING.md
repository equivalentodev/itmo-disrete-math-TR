# Как предлагать изменения

## Исправления

1. Получите свежий `main` и создайте свою ветку от него. Используйте логин в имени: `aldatov/tr2-fixes`, `ivanov/tr2-fixes`.
2. Редактируйте условия непосредственно в `TR/TRN/<номер задания>/<вариант>.tex`. Можно исправлять разные задания в одной ветке и одном PR.
3. Сохраните коммиты, отправьте ветку в общий репозиторий и откройте PR в `main`.
4. В PR укажите исправленные задания, что изменили и почему. Для математического исправления нужно обоснование.
5. После объединения начинайте следующую порцию правок от свежего `main`, не продолжайте старую объединённую ветку.

Пример начала работы из корня клона:

```sh
git fetch origin
git switch -c aldatov/tr2-fixes origin/main
```

Перед переключением веток сохраните свою незавершённую работу. Участники работают в ветках общего приватного репозитория; права на редактирование нужных веток выдаёт ответственный.

## Новая задача

- Номер задания выбирает автор. Скопируйте `templates/new-task/task.tex` в нужную папку банка с очередным числовым именем. Заполненный пример — `templates/new-task/example.tex`.
- Один файл — один вариант, начинается с `\question`. Пишите фрагмент, не полный документ: `\documentclass`, `\begin{document}` и собственные подключения пакетов не нужны.
- Файлы идут подряд: `1.tex`, `2.tex`, … Сохраняйте завершающий перевод строки.
- Рисунки помещайте в `TR/TRN/pic/`, в условии указывайте `pic/имя.png`. Выбирайте имя, которое не заменяет чужую иллюстрацию.
- Указывайте автора. Проверьте формулировку, данные, универсум дополнений, определения отношений и выполнимость требований.
- Решение обязательно приложите к **приватному PR** в комментарии или описании. Оно не должно лежать в `TR/`, шаблонах или итоговом архиве.
- Для просмотра используйте пункт «Подготовить типовик для проверки в Overleaf»: полученный ZIP загрузите в Overleaf и выберите `dump.tex` главным файлом. Обзор охватывает весь выбранный типовик.

Если два автора создали одинаковый следующий номер, это обычный конфликт, который решает принимающий PR. Сохраните оба новых условия: уже принятое оставьте под его номером, входящему назначьте следующий свободный номер. После разрешения проверьте непрерывную нумерацию. Утилита не резервирует номера и не исправляет конфликт сама.

При удалении вручную перенумеруйте оставшиеся варианты подряд. Ранее назначенный номер может начать обозначать другое условие — это принятое ограничение процесса. Не меняйте нумерацию без необходимости.

## Проверка и частичное принятие PR

Ответственный может убрать отклонённые изменения сам, не возвращая работу автору:

1. Получить ветку PR и переключиться на неё.
2. Для полностью отклонённого изменения вернуть файл к текущему состоянию `origin/main`; для частично отклонённого — отредактировать нужные строки.
3. Просмотреть разницу, закоммитить исправления и отправить их в **ту же ветку**.
4. Проверить обновившийся PR и объединить его в `main`.

Например, в ветке PR после `git fetch origin` команда ниже отклоняет все правки **только указанного файла**:

```sh
git restore --source=origin/main -- TR/TR2/4/7.tex
```

Отдельные коммиты по задачам и `cherry-pick` не обязательны. Обычный Merge принимает весь текущий PR; выбрать отдельные файлы галочками в нём нельзя.

## Что проверяет программа

Перед упаковкой программа проверяет структуру файлов, основные ошибки фрагментов, наличие рисунков, состав документов и ZIP. При именной сборке проверяет студентов и назначения. Это не математическая экспертиза и не подтверждение внешнего вида PDF. Компиляцию и просмотр выполняет человек в Overleaf.

Локальные тесты без установки Python:

```sh
docker compose run --build --rm -T utility python -m unittest discover -s tests -v
```

В Git должны попадать условия, рисунки, код и общие настройки. `work/` содержит только локальные входы, назначения и результаты; кроме каркаса и README они игнорируются. Папка `archive/` — запаска, в сборку не включается.
