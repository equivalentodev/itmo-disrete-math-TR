# План разработки утилиты

Дата: 21 октября 2026 года. Статус: первая версия реализована. Пункты ниже сохранены как план и критерии приёмки; фактические результаты — в [отчёте реализации](Утилита%20—%20реализация%20и%20проверка.md).

Обязательные продуктовые требования: [Утилита — принятые решения.md](Утилита%20—%20принятые%20решения.md). Ниже приведены порядок работ и технические решения для реализации. Технические имена и форматы ниже — предложенная реализация требований, а не дословные предпочтения пользователя.

## 1. Результат разработки

Одна Docker-утилита с русским меню для всех четырёх типовиков. Читает только актуальный банк `TR/`, готовит полные проекты для Overleaf, распределяет задания равномерно по потокам, сохраняет назначения и версионированные результаты. PDF не компилирует.

Первый запуск: клонирование → запуск Docker → помещение CSV в `work/students/` → выбор действия в меню. Работоспособность должна проверяться без ИИ и без установки Python на хосте.

## 2. Исходное состояние и ограничения миграции

- Рабочая реализация сейчас находится в `work/TR1/main.py`, использует стандартную библиотеку Python и обслуживает только ТР1.
- Она читает дубли условий из `work/TR1/tasks`, заново распределяет работы при каждом полном запуске и имеет зашитые ограничения по группе, десяти заданиям и реквизитам ТР1.
- Назначения текущей выдачи уже сохранены в `work/TR1/latex/assignments.csv`; их надо сохранить, а не заменить новым равномерным распределением.
- Актуальные банки при последней сверке: ТР1 — 79 файлов, ТР2 — 81, ТР3 — 77, ТР4 — 60. Количество номеров: 10, 11, 12, 9 соответственно. Перед миграцией перечитать фактический состав.
- В ТР3/ТР4 имеются известные проблемы ссылок на изображения; см. `docs/Очистка репозитория.md`. Не исправлять их и не подставлять одноимённые картинки автоматически. Ошибку сборки одного банка не превращать в запрет работы с другими.
- Условия и авторские подписи не менять. Не запускать LaTeX-компиляцию.

## 3. Целевая структура

```text
TR/
  TR1/ ... TR4/          # единственный редактируемый банк, внутри N/K.tex и pic/
archive/                # запаска, не источник для сборки
tool/                   # общий Python-пакет, точка входа и ядро
templates/              # общие шаблоны документа, просмотра и нового задания
config/project.toml     # название курса, учебный период и прочие реквизиты
tests/                  # проверки ядра и интеграционные сценарии
Dockerfile
compose.yaml
work/
  README.md             # отслеживаемая инструкция
  students/.gitkeep      # пользовательские CSV локальны
  assignments/.gitkeep   # локальные сохранённые назначения
  build/.gitkeep         # промежуточные проекты и отчёты
  exports/.gitkeep       # готовые ZIP и снимки метаданных версий
```

`.gitignore` исключает всё локальное содержимое `work/`, кроме инструкции и маркеров папок. Не добавлять содержимое CSV и именных документов в Docker build context. Рабочие входы и результаты подключаются при запуске; пакеты не скачиваются заново при каждой сборке типовика.

Использовать Python 3.12 и стандартную библиотеку, включая `tomllib`, `csv`, `zipfile`, `unittest`. На начальном этапе сторонние runtime-зависимости не нужны. Код ядра не зависит от терминального ввода: меню вызывает обычные функции, которые можно тестировать отдельно.

## 4. Пользовательские сценарии и интерфейс

Основное меню:

1. **Подготовить типовик для проверки в Overleaf.**
2. **Собрать работы для студентов.**
3. **Создать новое распределение.**
0. **Выход.**

Общие реквизиты читаются из понятного конфигурационного файла; не добавлять разработческие параметры в основной диалог.

### 4.1. Обзор

Выбрать типовик → проверить его условия и зависимости → сформировать весь просмотр → проверить комплект → записать новую версию ZIP и вывести точный путь.

Список студентов не нужен. В обзор входят все варианты в числовом порядке, никаких фамилий, назначений или решений. Сохранить компактное оформление и правильную нумерацию из нынешнего `render_review_variant`.

### 4.2. Именные работы

Выбрать типовик → CSV из `work/students/` → способ отбора «потоки / группы / все» → значения отбора → загрузить назначения → назначить отсутствующих и заменить несуществующие варианты → собрать по потокам → проверить → сохранить версию.

При первом запуске для данной выдачи назначения создаются автоматически. При следующих используются сохранённые. Перед сборкой показать число выбранных студентов и разбивку по потокам, чтобы ошибочный отбор был заметен. Это краткий итог выбранных настроек, а не отдельный абстрактный пункт меню.

### 4.3. Новое распределение

Выбор типовика, CSV и состава студентов такой же. Явное действие создаёт новое равномерное распределение выбранных студентов. Предыдущее распределение сохраняется версией; не заменять его необратимо. Невыбранных студентов не трогать.

Меню не выполняет Git-команды, не открывает PR и не принимает изменения. Техническая проверка встроена в сборку; отдельный пользовательский пункт «Проверить банк» не обязателен.

## 5. Ядро и данные

### 5.1. Чтение банка

- Папки номеров и `.tex`-файлы сортировать численно; `.DS_Store`, README и посторонние файлы не участвуют в вариантах.
- Номера заданий и вариантов должны идти с единицы последовательно. При пропуске показать точное место и не менять файлы автоматически во время сборки.
- Явная ручная перенумерация после удаления допустима. Инструкции объясняют её последствия для назначений.
- Фрагмент должен содержать одну команду `\question`. Проверять пустые файлы, основные незакрытые окружения, доступность изображений и безопасные пути внутри проекта. Не выдавать ограниченный статический анализ за полноценную LaTeX-компиляцию.
- Сохранять исходный текст. Добавление недостающего завершающего перевода строки при включении в документ допустимо; исходник не переписывать.
- Изображения брать из `pic/` именно выбранного банка. Никогда не искать автоматическую замену в `archive/`.

### 5.2. CSV и выборка

- UTF-8 с поддержкой BOM; обязательные колонки: `ИСУ ID`, `ФИО`, `Поток`, `Группа`. Дополнительные колонки допустимы и не влияют на генерацию.
- Отбирать по явно выбранным потокам/группам, без скрытого сравнения числовых частей групп.
- Проверять пустые обязательные значения, повторяющиеся ИСУ ID и пустой результат отбора; сообщать номер строки и причину.
- Идентификатор студента — ИСУ ID. Переименование ФИО и перестановка строк CSV не должны менять его сохранённые варианты.
- Перед включением ФИО в LaTeX экранировать специальные символы.

### 5.3. Сохранённые назначения

Предлагаемый внутренний формат — JSON со `schema_version`, учебным периодом, номером типовика, версией алгоритма, seed и записями по ИСУ ID. Каждая запись содержит ФИО, поток, группу и отображение «номер задания → номер варианта». Номера вариантов остаются обычными целыми числами; скрытые постоянные ID условий не вводятся.

Область назначений — учебный период + типовик. CSV-файл не является идентификатором распределения: обновлённый список того же периода должен находить прежних студентов. Текущий снимок хранится в `work/assignments/<период>/<типовик>/current.json`; предыдущие состояния — в отдельных версиях. Экспортируемая человекочитаемая таблица назначений имеет колонки для фактического числа заданий, а не десять захардкоженных колонок.

Обычная сборка:

- Сохраняет существующие допустимые номера.
- Обновляет ФИО и принадлежность к потоку/группе по входному CSV, не меняя варианты из-за изменения порядка строк.
- Для новых студентов и новых номеров заданий назначает недостающие варианты с учётом текущего использования и уникальности комбинаций.
- Если номера варианта больше нет, меняет только необходимые назначения и перечисляет замены в отчёте. Не обнуляет всю таблицу.
- Не интерпретирует изменение текста по прежнему пути как другую задачу.
- Если вследствие удаления/перенумерации появились одинаковые полные комбинации, автоматически исправляет минимально необходимую часть назначений и сообщает об изменениях. Это техническое следствие требования уникальности; не делать скрытое полное перераспределение.
- Не обещает строгую равномерность после добавления/удаления студентов, изменения потоков или точечных замен при замороженных назначениях. Строгая равномерность — гарантия нового распределения.

### 5.4. Равномерность и уникальность

Для каждого потока и каждого номера задания при новом распределении частоты всех вариантов должны быть `floor(N / K)` или `ceil(N / K)`, где N — число выбранных студентов потока, K — количество вариантов этого задания. Полные комбинации уникальны среди всех выбранных студентов.

Начать с детерминированного построения сбалансированных столбцов: выделять равномерные квоты, случайно выбирать получателей остатка, перемешивать столбцы по seed. Коллизии полных комбинаций устранять перестановками назначений внутри столбца одного потока: такие перестановки сохраняют его квоты. Проверять оба инварианта после построения, независимо от самого алгоритма.

До интеграции проверить подход на малых банках и почти заполненном пространстве комбинаций. Нельзя считать случайные повторы доказательством невозможности. Для малых трудных случаев предусмотреть точный поиск с квотами; для больших — ограниченные повторные попытки с однозначной ошибкой «не удалось построить распределение», без публикации частичного результата и без ложного заявления математической невозможности. Конкретный предел поиска зафиксировать в коде и тестах, без настройки пользователем в меню.

Если число студентов превышает произведение количеств вариантов, уникальное распределение заведомо невозможно: сообщить числа и не выдавать повторяющиеся работы молча. При повторной сборке учитывать сохраняемые назначения и не менять их только ради получения более красивой статистики.

## 6. Шаблоны, версии и упаковка

- Перенести существующее оформление в общие шаблоны. Номер типовика и учебный период подставлять из данных, а не исправлять шаблон для каждого банка.
- Перед переносом перечитать актуальные шаблоны: пользователь мог редактировать их вручную. Переносить текущее состояние, не восстанавливать оформление по памяти.
- Для обзора: один `dump.tex` и нужные рисунки. Для именных работ: `flow_<номер>.tex` для каждого выбранного потока и нужные рисунки. Не включать обзор в именной проект автоматически без необходимости.
- В каждый ZIP добавить короткую инструкцию с именами главных файлов и указанием загрузить архив как проект Overleaf. Инструкция не содержит внутренних абсолютных путей.
- Служебные временные файлы, Python-код, CSV-источник, решения и `archive/` в ZIP не попадают.
- Именной ZIP содержит имена в самих работах; таблица назначений и метаданные версии сохраняются рядом с ZIP, вне компилируемого проекта.
- Имена версий включают типовик, назначение `review`/`students` и время UTC до секунд; при совпадении времени добавлять числовой суффикс. Прежний ZIP никогда не перезаписывать.
- Рядом сохранять manifest: версия схемы, время, тип сборки, реквизиты, отбор студентов, seed/версия распределения, количества студентов по потокам, контрольные суммы условий, шаблонов, рисунков и входного CSV, SHA-256 ZIP. При наличии Git — commit и признак локальных изменений; отсутствие `.git` не препятствует запуску.
- Для именной версии сохранять точный снимок назначений. ZIP самодостаточен для сборки; manifest и снимок нужны для воспроизводимости и разбора выдачи.
- Сначала готовить всё во временном каталоге, затем проверять и публиковать готовую версию. При ошибке не оставлять новый «готовый» ZIP и не повреждать предыдущие назначения. Избежать одновременной записи двумя запусками в одну область назначений.

## 7. Docker и переносимость

- Один небольшой образ Python без LaTeX и без веб-сервера. Не устанавливать зависимости на хост.
- Подключить корень проекта, работать с одинаковыми путями внутри контейнера. Поддержать интерактивный ввод и вывод в русской UTF-8 локали.
- Предусмотреть понятную обработку `Ctrl+C` и ошибок: выход без разрушения предыдущих результатов, короткое сообщение с причиной, без обязательного чтения traceback.
- Проверить пути с пробелами и кириллицей, доступ к выходным файлам на Linux и запуск на Windows/macOS через Docker Desktop. Избегать обязательных POSIX-команд в пользовательских сценариях.
- Подготовить образ для amd64 и arm64 либо явно проверяемый способ сборки на обеих архитектурах.
- Размер проверять по размеру распакованного образа из Docker image inspect: порог 512 МБ. Не выдавать размер сжатой загрузки за размер образа. Если превышен — остановиться и обсудить с пользователем.
- Опубликовать одну рекомендуемую команду запуска через Compose. Список входных CSV и сохранение результатов должны работать без изменения Dockerfile/compose под конкретного пользователя.

## 8. Миграция существующих материалов

1. Зафиксировать перечень и контрольные суммы исходных условий, текущих шаблонов, CSV, назначений и готового ZIP ТР1.
2. Сверить `TR/TR1` с `work/TR1/tasks`. Не перезаписывать молча обнаруженные различия: сохранить их для разбора и сообщить пользователю.
3. Перенести код и актуальные шаблоны из `work/TR1` в общее место; адаптировать для всех банков.
4. Перенести список студентов в `work/students/`. Импортировать старые назначения ТР1 без изменения комбинаций и без применения новой равномерности задним числом.
5. Существующий готовый архив и связанные с ним назначения сохранить как исторический локальный результат. Предварительные документы перенести в `work/build/legacy-TR1/`.
6. Только после сверок убрать дубли условий, шаблонов, рисунков и кода из старой `work/TR1`. Не удалять единственные пользовательские данные. Фактические задачи остаются в `TR/` побайтно прежними.
7. Добавить каркас `work/` и правила игнорирования. Обновить `README.md`, `AGENTS.md` и рабочие инструкции: запретить возвращение к двум редактируемым банкам.

## 9. Документация для коллег

- Короткий старт: клонирование, Docker, место CSV, два способа сборки, где искать готовый ZIP.
- `CONTRIBUTING.md`: ветка с логином, исправление разных задач одним PR, оформление нового варианта, решение в комментарии PR, конфликты одинаковых номеров, действия ответственного при частичном принятии.
- Шаблон условия `.tex` и один небольшой заполненный пример в отдельной папке шаблонов, вне банка. Не добавлять пример в реальные задания. Авторская подпись и размещение рисунков показаны явно.
- Шаблон PR: список файлов/задач, смысл изменения, обоснование; для нового задания — напоминание приложить решение в комментарии. Не заводить обязательный файл решения.
- Ответственный передаёт следующему человеку доступ и инструкции; настройки и код не должны зависеть от имени нынешнего ответственного.
- Не настраивать PDF-превью, Actions-компиляцию или автоматический merge. Публикацию приватного репозитория выполнять отдельным явно порученным действием.

## 10. Порядок реализации

1. **Ядро входных данных и структуры.** Читатель банков, конфигурация, CSV, выборка, сообщения об ошибках. Тесты на синтетических данных; условия не менять.
2. **Назначения.** Формат хранения, импорт ТР1, создание сбалансированных уникальных комбинаций, повторная сборка и точечные изменения. Сначала доказать инварианты тестами, затем подключать меню.
3. **Формирование проектов и архивов.** Общие шаблоны, обзор, потоки, рисунки, версии, manifest и атомарная публикация.
4. **Меню и Docker.** Минимальные диалоги, обработка ошибок и переносимость. Не добавлять новые функции вместо завершения согласованных сценариев.
5. **Миграция и инструкции.** Перенос существующих локальных данных, удаление дублей только после сверок, README, AGENTS, CONTRIBUTING, примеры и PR-шаблон.
6. **Приёмка.** Прогон всех согласованных сценариев, проверка Docker и размера, выдача пользователю команд запуска и расположения результата. PDF не компилировать.

## 11. Проверки и критерии готовности

### Банки и документы

- ТР1 с 10 и ТР2 с 11 номерами читаются без правок кода; тесты также покрывают фактические 12 и 9 номеров остальных банков.
- Все числовые варианты попадают в обзор ровно один раз и в правильном порядке. Окружение `questions` не сбрасывает выбранный номер: счётчик устанавливается внутри него перед `\question`.
- В обзоре нет фамилий студентов, повторяющихся шапок между условиями и принудительных разрывов страницы.
- Каждый выбранный студент включён ровно один раз в файл своего потока и получает все номера заданий.
- Тексты включённых условий соответствуют актуальным исходникам, экранируются только генерируемые пользовательские поля.
- ZIP содержит все нужные рисунки, их байты совпадают с банком; ссылки разрешаются внутри проекта. Отсутствующий рисунок даёт точное сообщение и не создаёт неполный финальный архив.

### Распределение

- Для нескольких потоков разного размера проверить отличие частот не более одного отдельно по каждому номеру задания и потоку.
- Проверить уникальность полных комбинаций между всеми выбранными потоками, включая малые банки с высокой вероятностью коллизий и заполнение пространства комбинаций до предела.
- Проверить воспроизводимость нового распределения при фиксированных seed и входах. Перестановка строк CSV не меняет сохранённые назначения.
- Исправление текста и повторная сборка не меняют назначений; новый студент не перераспределяет прежних.
- Недоступный номер автоматически заменяется, замена сохраняется и отражается в отчёте; остальные номера сохраняются.
- Новое распределение — отдельное действие, предыдущая версия остаётся доступной. Старый импортированный ТР1 не выравнивается автоматически.
- Недостаточное число комбинаций, дубли ИСУ ID и пустая выборка дают понятную ошибку, не публикуя невалидный результат.

### Версии, миграция, запуск

- Две сборки не перезаписывают прежние ZIP; у каждой есть соответствующий снимок назначений и manifest.
- Прерванная/ошибочная сборка оставляет предыдущие готовые результаты и назначения исправными.
- После миграции все реальные условия побайтно сохранены, списки студентов и историческая выдача не потеряны, единственный редактируемый банк — `TR/`.
- В Git не должны попадать локальные CSV, назначения и результаты; при этом новый клон получает каркас `work/`.
- Коллега может оформить новую задачу по примеру, получить полный обзорный ZIP, открыть PR и приложить решение без ИИ.
- Запуск из Docker не требует Python или TeX на хосте; размер образа не превышает оговорённые 512 МБ либо превышение отдельно согласовано.
- Фактический просмотр PDF пользователем в Overleaf остаётся проверкой внешнего вида; автоматические тесты исходников его не заменяют.
