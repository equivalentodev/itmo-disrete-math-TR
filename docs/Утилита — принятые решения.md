# Утилита и совместная работа: принятые решения

Дата фиксации: 21 октября 2026 года.

Назначение: память для агента и основа разработки. Это результат обсуждения с пользователем, а не описание уже реализованной программы. План реализации: [Утилита — план разработки.md](Утилита%20—%20план%20разработки.md).

## 1. Цель

Дать ответственному и коллегам понятный воспроизводимый процесс подготовки типовых расчётов без обязательного участия ИИ. Новый ответственный в следующем году должен уметь работать по документации, а не восстанавливать договорённости по переписке.

Утилита обслуживает все четыре типовика, подготовку материалов для проверки и именных работ. Математическое содержание проверяют люди; программа не объявляет условия математически правильными и не переписывает их самостоятельно.

## 2. Работа команды и GitHub

- Репозиторий планируется **приватным**.
- Участники: ответственный, проверяющие старые условия, авторы новых задач. Сейчас решения о принятии принимает пользователь; в будущем проверяющих и принимающих может быть несколько.
- `main` содержит принятые условия. Коллеги работают в отдельных ветках общего репозитория и открывают PR в `main`.
- Один проверяющий может исправлять разные задачи в одной ветке и одном PR. Не требовать отдельную ветку/PR на опечатку или файл.
- Имена веток включают логин автора, например `aldatov/tr2-fixes`, `ivanov/tr2-fixes`. В пределах общего репозитория одинаковое имя означало бы одну ветку.
- После завершения PR следующая порция работы начинается от обновлённого `main`; не накапливать год работы в одной старой ветке.
- Чтобы принять лишь часть PR без обращения к автору, ответственный переключается на его ветку, сам убирает отклонённые изменения, делает коммит, отправляет его в эту же ветку и объединяет обновлённый PR.
- Не делать отдельные коммиты по задачам и `cherry-pick` обязательным рабочим процессом. Не обещать выбор отдельных файлов галочками при обычном Merge: такой операции нет.
- PR кратко объясняет, какие условия изменены и почему. Для исправлений — обоснование. Для новых задач решение обязательно при проверке.
- Создание репозитория, публикация и настройка GitHub — последующий отдельный этап; обсуждение не означает, что репозиторий уже создан.

## 3. Новые задания и решения

- Автор сам выбирает номер задания соответствующего типовика.
- Автор оформляет условие в LaTeX по понятному шаблону и заполненному примеру. Приём обычного текста для последующего перевода ответственным не предусматривается.
- Сохраняются сведения об авторстве; необходимые рисунки автор добавляет вместе с условием.
- Новые варианты добавляются сразу в `TR/TRN/<номер задания>/`.
- Файлы вариантов именуются последовательно: `1.tex`, `2.tex`, `3.tex`, … Без UUID, авторских имён в названиях файлов и промежуточной папки предложений.
- Одновременное добавление вариантов с одинаковым номером возможно и ожидается. Совпадения разрешаются людьми при объединении PR; отдельную систему резервирования номеров не строим.
- Автор прикладывает решение в описании или комментариях PR. Решения не становятся файлами банка и не попадают в студенческие и обзорные архивы. Они остаются доступными участникам приватного PR.
- Автор может предложить несколько вариантов. Ответственный может принять лишь некоторые; специальный интерфейс выборочного приёма для этого не нужен.

## 4. Структура проекта

- `TR/` — **единственный актуальный редактируемый банк** условий и рисунков всех типовиков.
- Дубли условий в `work/` должны исчезнуть при миграции. Больше нет процесса синхронизации двух редактируемых копий.
- Генератор, общие шаблоны, примеры и настройки хранятся вне `work/` и доступны через Git.
- `work/` — локальная рабочая область. В Git остаётся только её каркас с инструкцией; входные списки, назначения, промежуточные файлы и результаты в Git не попадают.
- Внутри `work/` отделяются: папка для CSV студентов, предварительные результаты и готовые версионированные архивы для Overleaf. Назначения также хранятся локально.
- `archive/` — запасные старые условия и рисунки. Обычно не используется и автоматически в генерацию не включается.
- Содержательные изменения в Overleaf не возвращаются в банк автоматически. Исправления необходимо переносить в `TR/`, затем пересобирать материалы.

## 5. Запуск и интерфейс

- Стандартный способ запуска — Docker. После клонирования на macOS, Windows и Linux с установленным Docker не требуется вручную ставить Python и зависимости.
- Интерфейс — **меню в терминале на русском языке**.
- Пункты обозначают понятные действия и результат, без «состояния сборки», «состава банка» и похожих абстрактных названий.
- Пользователь не должен помнить отдельные этапы копирования рисунков, проверки состава или упаковки ZIP. Нужные проверки выполняются в рамках выбранного действия.
- Доступ к генерации не разграничивается по ролям внутри утилиты. Коллеги могут запускать её; окончательную выдачу готовит ответственный.
- Ориентир размера Docker-образа — **не более 512 МБ**. Если уложиться не удаётся, сначала обсудить с пользователем, а не молча принять более тяжёлый образ.

## 6. Сборка и просмотр

- Финальная компиляция PDF — **только в Overleaf**.
- Локальная компиляция, установка TeX Live в Docker, автоматическое открытие PDF и слежение за сохранением `.tex` исключены из текущей версии.
- Автоматические PDF/PNG-превью в GitHub PR и сборка таких превью через Actions также исключены. Коллеги редактируют исходники и присылают PR.
- Под сборкой понимается **выбранный типовик целиком**, а не отдельное условие или произвольный набор файлов.
- Есть два результата:
  1. Обзорный ZIP для проверки всего банка выбранного типовика: все варианты по возрастанию номера задания и варианта, без студенческих фамилий.
  2. ZIP именных работ выбранного типовика: отдельный самостоятельный `.tex` для каждого выбранного потока, со всеми нужными рисунками.
- Для обзора сохраняются ранее согласованные требования: перед условием только «Вариант N», номер самого задания правильный, повторяющихся шапок между условиями нет, принудительных разрывов страницы между вариантами нет.
- В именных документах сохраняется оформление существующих работ и разделение работ разных студентов.
- Готовый ZIP загружается как проект Overleaf. Не требовать вручную собирать его из нескольких исходных папок или докладывать рисунки.
- Старые финальные архивы **сохраняются и версионируются**, не перезаписываются. С версией сохраняется использованное распределение.
- Предварительные файлы допускается обновлять при следующем запуске. Они отделены от финальных ZIP.

## 7. Студенты и распределение

- Входной формат — CSV, как в текущем списке: `ИСУ ID`, `ФИО`, `Поток`, `Группа`. Не добавлять обязательный XLSX.
- Пользователь помещает CSV в локальную папку и выбирает файл, затем нужные потоки или группы в меню.
- Зашитое в код ограничение «от M3111» и исключение потоков 1–2 удаляются. Отбор задаёт пользователь.
- Выбор групп определяет состав студентов, но итоговые документы **всегда разделены по потокам**. Отдельную сборку по группам и один общий именной файл не добавляем.
- Каждый выбранный студент получает по одному варианту каждого номера задания.
- При создании **нового распределения** каждый вариант каждого номера задания используется максимально равномерно **внутри каждого потока**: число назначений разных вариантов отличается не более чем на единицу.
- Полные комбинации вариантов должны быть уникальны среди всех выбранных студентов, в том числе между потоками. Это уникальность комбинаций номеров файлов, не гарантия различия содержания повторяющихся условий.
- Назначения сохраняются. При исправлении текста и обычной пересборке студент получает прежние номера вариантов с актуальным текстом.
- Перераспределение всех студентов — отдельное явно выбранное действие, не побочный эффект сборки.
- Новому студенту назначаются варианты без перераспределения остальных. При сохранённых назначениях это не должно превращаться в скрытое полное выравнивание.
- Добавление нового варианта не перераспределяет старые работы. Строгая равномерность всего потока снова обеспечивается при явном создании нового распределения.
- При удалении вариантов имена оставшихся файлов должны снова идти последовательно. Пользователь принимает, что вследствие перенумерации у части студентов может измениться содержание назначенного номера. Не вводить запрет удаления после назначения и не строить систему постоянных скрытых ID ради защиты от этого сдвига.
- Если назначенный номер после удаления отсутствует, автоматически выбрать допустимую замену, сохранить её и сообщить о замене. Остальные назначения не пересчитывать без необходимости.

## 8. Что не добавлять без нового поручения

- Обязательные решения в файлах банка, отдельное хранилище решений.
- Публичный репозиторий вместо выбранного приватного.
- Локальный PDF-компилятор и превью в PR.
- Веб-приложение, сервер/VPS, авторизацию и разграничение возможностей утилиты.
- UUID в именах вариантов, `proposals/`, автоматическое принятие PR или резервирование номеров.
- Автоматическую математическую проверку или переписывание условий.
- Сборку отдельной задачи, выбранных файлов, групповых или общих именных документов.
- Повторное обсуждение уже выбранных решений без конкретной обнаруженной несовместимости.
